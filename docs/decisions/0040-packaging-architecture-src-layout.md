# 0040 Packaging architecture: src-layout darwin package, hatchling, walk-up resolver, console scripts; not published to PyPI

Decision: The flat `tools/` scripts are converted into an installable, importable `darwin` package laid out src-style under `src/darwin/`, with the test suite moved to `tests/` (outside the package). The build backend is hatchling, configured for the src layout. A single `paths.py` resolver locates the data directories by walking up from a starting file to the first ancestor holding a marker. Six `darwin-*` console scripts are declared for the argparse-driven harnesses. The package is built and `pip install .` works, but Darwin is still NOT published to PyPI. This is the v0.8 packaging milestone (version 0.8.0, decision references throughout this record).

Context: Before v0.8 the code lived as flat scripts under `tools/` with bare imports (`import paths`, `import evaluator`), runnable only from inside that directory on a manually set `PYTHONPATH`. That blocked a real install: there was no package to install, no entry points, and no build metadata that produced a working artifact. v0.8 converted the layout in stages, all audited:

- P8.2 moved the modules to `src/darwin/` and the tests to `tests/`, rewrote every bare import to an absolute `darwin.*` import, and replaced each module's fixed `Path(__file__).parent.parent` data-root guess with a single resolver in `paths.py`. The resolver walks UP from a starting file to the first ancestor that holds a marker (`pyproject.toml` or a `cases/` directory), so the resolved root is correct no matter how deeply a module is nested (under `src/darwin/` or `tests/`); precedence is an explicit in-process override (a CLI flag value) first, then `DARWIN_DATA_ROOT`, then the walk-up. The data directories (`cases/`, `mcases/`, `runs/`, `reports/`, `seeds/`) stay at the checkout root, OUTSIDE the package.
- P8.3 added the `[build-system]` table (hatchling) and the six console scripts, and pointed the wheel target at `src/darwin` so the wheel ships only the package.

The build backend is hatchling because it supports the src layout out of the box (it discovers the `darwin` package under `src/`) with minimal configuration and is already a maintained, widely used backend; no plugin or custom build step is needed. The wheel target `[tool.hatch.build.targets.wheel] packages = ["src/darwin"]` makes the wheel ship the `darwin` package and nothing above it, so `cases/`, `mcases/`, and the `docker/` build infrastructure (including the seccomp example) stay OUT of the wheel.

The console-script set is exactly the six argparse-driven harnesses that a user runs as commands: `darwin-loop`, `darwin-mloop`, `darwin-benchmark`, `darwin-mbenchmark`, `darwin-variance`, and `darwin-isolation-audit`, each mapping `darwin-<name>` to the module's existing zero-argument `main()`. The four non-argparse harnesses (`bakeoff`, `smoke_test`, `build_case`, `validate_mcase`) get NO console script by design: they are authoring and diagnostic dev tools, run as `python -m darwin.<name>`, and putting them on `PATH` would imply an end-user command surface they are not.

Not published to PyPI: this is a deliberate, standing decision, not an oversight. Darwin is a single-author research engine with an honest early-release posture (0.x, decision 0005), soft multi-file references, a small validation corpus, and an open in-process verdict-forgery residual (decision 0008). Publishing to PyPI would invite drive-by installs of something that explicitly makes no benchmark-grade or production-grade claim, and would create a name-squat and a maintenance-and-yank obligation. Darwin stays a GitHub-tagged release installed from a checkout. The convenience-versus-supported install-path policy is recorded separately (decision 0041); the import-time-resolution deferral that makes the installed CLIs actually run is recorded in decision 0042.

Alternatives rejected:
- Keep the flat `tools/` layout on a manual `PYTHONPATH`: rejected. It is not installable, has no entry points, and forces every invocation to run from one directory; the whole point of v0.8 is a real install path.
- setuptools instead of hatchling: rejected. setuptools would work, but it needs more configuration for a clean src layout and a controlled wheel manifest; hatchling gives the same result with less config and no measurable benefit lost. This is a low-stakes backend choice and hatchling is the simpler one here.
- A fixed `Path(__file__).parent.parent` data root (the pre-conversion idiom, re-depthed): rejected. The depth is wrong the moment modules are nested under `src/darwin/` or `tests/`, and it cannot serve an installed CLI that has no checkout above the module. The walk-up resolver with an env-var and flag override is correct for both the checkout and the installed cases.
- Console scripts for all ten harnesses: rejected. The four non-argparse harnesses are dev tools with no end-user command contract; exposing them on `PATH` would overstate the surface. They stay `python -m darwin.<name>`.
- Publish to PyPI: rejected, as above. The honest-early-release posture and the open residual make a public package premature; GitHub-tagged from a checkout is the right distribution for this stage.

Consequences: `pip install .` builds a hatchling wheel that ships only the `darwin` package and puts the six `darwin-*` console scripts on `PATH`. The package imports as `darwin.*` from anywhere; data resolution is centralized in `paths.py`: an installed run is pointed at its data with `DARWIN_DATA_ROOT`, while the per-command directory flags (`--cases-dir` / `--mcases-dir` / `--out`) override only their own lookup and do not on their own satisfy an installed run, which also resolves `runs/` (and `reports/`) under the data root. The four non-console harnesses remain `python -m darwin.<name>`. Darwin is not published to PyPI; it stays GitHub-tagged and installed from a checkout. No optimization, scoring, equivalence, generator, evaluator, or sandbox behavior changed: the conversion is a layout-and-packaging change. The install-path supply-chain policy (decision 0041) and the import-time-resolution deferral (decision 0042) build on this record.
