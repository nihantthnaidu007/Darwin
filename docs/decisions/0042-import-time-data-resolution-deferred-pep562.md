# 0042 Data-root resolution deferred out of import time via PEP 562 lazy module attributes

Decision: No module under `src/darwin` resolves a data path at import. Each module that exposes a data-directory module attribute (for example `CASES`, `MCASES`, `RUNS`, `REPORTS`) resolves it LAZILY, at first attribute access, through a module-level `__getattr__` (PEP 562) that calls the `paths.py` resolver. The lazy attribute stays settable and monkeypatchable: an explicit assignment to the module attribute (by another module or a test) shadows the lazy default, because an assigned module global wins over module `__getattr__`. Functions read the attribute through the module object (for example `_THIS.CASES`, where `_THIS = sys.modules[__name__]`) rather than a bare name, so the lazy default and any override are both honored.

Context: Resolving a data path at import is a defect once the package is installable. An installed console script has no checkout on disk, so a module that ran `CASES = paths.cases_dir()` at module scope crashed at `import` time -- before `main()` ran, before argparse could supply `--cases-dir` or the caller could set `DARWIN_DATA_ROOT`. The packaging audit (P8.3) found this broke the installed CLIs: even `darwin-loop --help` raised the resolver error, because importing the module to reach its `main` already tried to resolve a data root that does not exist for an installed CLI. Import-time filesystem work is the wrong place for resolution that depends on runtime configuration.

The fix is a deferral, not a behavior change. P8.3 converted the six console-script entry points to the PEP 562 lazy-attribute pattern. P8.4 converted the last four standalone harnesses that still resolved at module scope -- `bakeoff` (`CASES`), `smoke_test` (`CASES`), `build_case` (`CASES_DIR`), and `validate_mcase` (`MCASES`) -- using the identical pattern, with no second mechanism invented. After P8.4 no `src/darwin` module does filesystem work at import.

The mechanism, stated once: a module sets `_THIS = sys.modules[__name__]` and defines `def __getattr__(name)` that returns `paths.cases_dir()` (or the relevant resolver call) for the data attribute and raises `AttributeError` otherwise. Module `__getattr__` (PEP 562) fires only for attribute access on the module object that does not resolve to a real attribute, so functions must read `_THIS.<ATTR>` rather than the bare global `<ATTR>` -- a bare-name lookup inside a function does not trigger module `__getattr__` and would raise `NameError`. Reading through the module object means an assigned real attribute (a CLI override in `main`, or a test's `monkeypatch.setattr(module, "MCASES", tmp_path)`) shadows the lazy default, preserving the settable/patchable behavior callers depend on. Resolution still raises the same clear, actionable `RuntimeError` from `paths.data_root()` when no data root is locatable -- now at first use, with an exit, rather than as an import-time crash.

Alternatives rejected:
- Keep module-scope resolution but wrap it in `try/except`: rejected. That still does filesystem work at import and hides the failure instead of removing it; the installed `--help` path would silently swallow the resolver error or carry a `None` sentinel into later code. Deferral removes the import-time work entirely.
- A config singleton or an explicit `init()` call every module must invoke first: rejected. It adds a new mechanism and a new ordering obligation across many modules for no gain over the PEP 562 attribute, which resolves on demand with no caller ceremony.
- A second, different deferral pattern for the four P8.4 harnesses: rejected. The six entry points already use the PEP 562 lazy attribute; the task constraint is to use the identical pattern, so a divergent mechanism would be gratuitous inconsistency.
- Drop the settable attribute and resolve only inside functions: rejected. `benchmark.py`, `mbenchmark.py`, and several tests set the module attribute directly (for example `loop.CASES = ...`, `monkeypatch.setattr(validate_mcase, "MCASES", ...)`); the `_THIS.<ATTR>` indirection preserves that exactly, while a function-local resolution would break the override seam.

Consequences: Every `src/darwin/*.py` module imports cleanly in a clean virtualenv outside any checkout with no `DARWIN_DATA_ROOT` set; the import-safety proof imported all 36 package modules with zero failures (36 of 36). A grep for module-scope data resolution (`= paths.cases_dir()` / `mcases_dir()` / `data_root()`) returns nothing. The installed console scripts run `--help` and honor `--cases-dir` / `--mcases-dir` / `DARWIN_DATA_ROOT` without a checkout on disk. The settable/patchable attribute behavior is preserved, so the benchmark drivers and the existing tests are unchanged. No optimization, scoring, equivalence, generator, evaluator, or sandbox behavior changed: this is an import-time deferral, behavior-preserving, identical in kind to the P8.3 remediation.
