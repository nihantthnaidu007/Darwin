# 0033 Opt-in defense-in-depth (seccomp hook, example profile, multi-tenant guidance)

Decision: Add opt-in, off-by-default plumbing to inject extra container security options (an additional seccomp profile and related `--security-opt` hardening) on top of the 1.0 lockdown, ship a clearly-labeled EXAMPLE seccomp profile as a starting point, and document the multi-tenant hardening posture in SECURITY.md. The default `docker run` argv is byte-for-byte unchanged: with no opt-in set, the produced argv is identical to today's. This phase adds restriction only as an opt-in; it removes or alters no lockdown flag, and it enables nothing by default.

Why opt-in and off by default: the 1.0 threat model is single-user-trusted (you run your own simplifier on your own host), and the existing lockdown (cap-drop ALL, no-new-privileges, non-root, read-only root, network none, memory/CPU/PID caps, CI-verified on cgroup v2 in P6.3) is sufficient for it. A multi-tenant 2.0, where untrusted tenants share a host, wants more syscall-level and resource-fairness hardening. Building that hardening as opt-in plumbing now lets a multi-tenant operator turn it on at deployment without a code change and without forcing any cost or behavior change on the 1.0 single-user path. A VALIDATED production seccomp profile is itself 2.0 work (it requires validating the syscall set against the real workload), so 1.0 ships the hook and a labeled example, not a validated artifact.

Mechanism, env var over a threaded parameter (and why): the opt-in is the environment variable `DARWIN_SANDBOX_EXTRA_SECURITY_OPTS`, read ONCE at module load into the module-level `EXTRA_SECURITY_OPTS` (a comma-separated list of docker `--security-opt` values, for example `seccomp=/abs/path/example-sandbox-seccomp.json`). This mirrors the operator-side `DARWIN_LOG_*` convention already in `logsetup`: it is deployment configuration, not a per-call argument, so a multi-tenant operator hardens the deployment from the environment without editing code, and no consumer signature changes. `_run_argv` also takes an `extra_security_opts` keyword (defaulting to None -> the module-level value, read at CALL time so both the env var and tests take effect) so the appending is directly unit-testable. A comma is the list separator; values containing a comma (some SELinux label opts) are not expressible by the env var by design, which the common seccomp/apparmor case does not need.

Byte-identical-default guarantee and how it is enforced: the extras are spliced into the argv via `*_extra_security_opt_args(opts)` immediately after the existing `--security-opt no-new-privileges`. When `opts` is empty (the default, env unset), that expands to zero elements, so every other element of the list literal is unchanged and the produced argv is byte-identical to the prior lockdown. When non-empty, each entry is appended as an additional `--security-opt <value>` and nothing else moves: the original flags keep their order and values. A test pins the exact current argv and asserts the no-opt-in argv equals it; a second test asserts that with the opt-in set the extra `--security-opt` entries appear, the `--security-opt` count is the original one plus the extras, `no-new-privileges` is intact, and stripping the extra pairs reproduces the byte-identical default (so the extras are provably purely additive). The env-var parsing and the call-time read of the module-level opt-in are also tested.

The example profile is a labeled STARTING POINT, not a validated artifact: `tools/seccomp/example-sandbox-seccomp.json` is labeled EXAMPLE in its filename and in inline `comment` fields, and the accompanying note in SECURITY.md's multi-tenant hardening section states the same, all requiring it be validated against the real workload before any multi-tenant use. It uses `defaultAction: SCMP_ACT_ALLOW` and denies (via `SCMP_ACT_ERRNO`, which returns EPERM rather than killing) a curated set of administrative, namespace, and kernel syscalls (mount, ptrace, kexec, kernel-module ops, bpf, keyring, clock-set, and similar) that an untrusted candidate has no reason to call and that a normal python+pytest run does not use. Most already require capabilities that `--cap-drop ALL` removes, so this is belt-and-suspenders defense-in-depth, deliberately NOT a tight default-deny allowlist; a production profile should invert to default-deny with a validated allowlist. No architectures are pinned, so the example applies on every architecture (the arm64 dev host and the x86_64 CI runners alike).

Smoke test, explicitly not a validation: the repo confirms only that wiring the example profile through the opt-in path lets a normal python+pytest candidate still run (it does not break the workload). This is verified two ways: an automated Docker-gated test (`tools/test_sandbox_argv.py`) that monkeypatches the opt-in to the example profile and asserts a good candidate scores OK, and the existing end-to-end probe (`tools/verify_container_sandbox.py`) run with `DARWIN_SANDBOX_EXTRA_SECURITY_OPTS` set to the profile, which still reports all nine lockdown guarantees held. Both are described as a SMOKE TEST, not a security validation: they prove the profile does not break the normal workload, not that it blocks any real attack and not that the syscall set is correct for a given workload.

SECURITY.md multi-tenant hardening section: the "Optional future hardening (noted, not built)" section is replaced by a "Multi-tenant hardening (opt-in, off by default at 1.0)" section documenting (a) seccomp via the opt-in path with the shipped example, (b) daemon-level user-namespace remap as Docker daemon configuration (`userns-remap`), explicitly operator-side and not a per-container flag, documented but not enabled here, and (c) block-IO caps (`--blkio-weight` / `--device-write-bps`) and a file-size cap (`--ulimit fsize`), noting the writable-area size cap already present at 1.0 (the in-RAM `/tmp` tmpfs created with a fixed `size=64m`). Each item is marked multi-tenant guidance, off by default at 1.0; the section states plainly that 1.0 enables none of them by default and ships only the seccomp opt-in plumbing plus the labeled example.

Deferred to the multi-tenant 2.0 work: validating a production seccomp profile against the real workload, and enabling daemon-level user-namespace remapping (operator-side daemon configuration). Both are documented here as the recommended posture; neither is built or enabled in this phase.

Out of scope and unchanged: the default lockdown flags (unchanged; opt-in only adds restriction on top), a validated production seccomp profile (the shipped one is an example), enabling user namespaces, the verdict-emission seam (P6.4.2, decision 0032), the pytest CVE bump (P7.2), and all gate, scoring, equivalence, generation, and single-function-legacy logic.

Consequences: a multi-tenant operator can layer a seccomp profile (and other `--security-opt` hardening) onto the sandbox by setting one environment variable, with a labeled example to start from, while the 1.0 single-user default path is byte-identical and unaffected. The repo carries the opt-in plumbing, the example profile and its starting-point labeling, the byte-identical-default and additive-only tests, the smoke-test evidence, and the documented multi-tenant posture (seccomp, userns, block-IO and file-size caps). No default-lockdown flag was removed or altered, and no gate, scoring, generation, or single-function-path logic changed.
