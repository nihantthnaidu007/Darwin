# 0028 Hash-locked dependency lockfiles with pip-tools

Decision: Dependency installs are made reproducible and hash-verified across the host, CI, and the sandbox image. Three pip-tools `.in` sources are compiled with `pip-compile --generate-hashes` into three fully hash-locked lockfiles, and every install path enforces the hashes with `pip install --require-hashes`:

- `requirements.in` -> `requirements.txt` (host runtime closure, hashed)
- `requirements-dev.in` -> `requirements-dev.txt` (runtime + dev tools, hashed; what CI installs)
- `tools/requirements-sandbox.in` -> `tools/requirements-sandbox.txt` (pytest closure only, hashed; what the Dockerfile installs)

No dependency is upgraded. The direct runtime versions are byte-identical to before (radon==6.0.1, vulture==2.16, pytest==8.3.5, anthropic==0.107.1, httpx==0.28.1); this phase adds the transitive pins and the hashes and wires `--require-hashes`, nothing more. The `.in` files are the source a maintainer edits; the `.txt` files are generated and never hand-edited.

Regeneration procedure (pip-tools is the maintainer-only tool; it is not in any install path): install pip-tools into a Python 3.13 environment and run, from the repo root,

    pip-compile --generate-hashes --output-file=requirements.txt requirements.in
    pip-compile --generate-hashes --output-file=requirements-dev.txt requirements-dev.in
    pip-compile --generate-hashes --output-file=tools/requirements-sandbox.txt tools/requirements-sandbox.in

Edit a `.in` file (a direct pin, or the dev/sandbox tool list), recompile the affected lock, and commit both. The `.txt` files carry the pip-compile header naming the source `.in` and the command. The same compile commands are recorded in each `.in` file's header.

Context: A2 and G2 flagged that the requirements files pinned direct versions but carried no hashes and no transitive lock, so a clean install was not reproducible (transitive versions floated) and the dependency surface was not auditable or tamper-evident. Pinning every transitive package and recording per-artifact hashes makes a clean environment resolve to the exact locked, hash-verified set, and makes `pip` reject any artifact whose content does not match the lock.

Canonical compile environment is Python 3.13, the CI and container version. Compiling on one interpreter keeps the lock and its environment markers deterministic. The dev host is Python 3.14, so the lock must install on 3.12 through 3.14 from a single 3.13-compiled file; `--generate-hashes` makes that work, see below. Compilation was verified on Python 3.13 (pip-tools 7.5.3).

`--generate-hashes` cross-version rationale: this flag records the sha256 of every distribution file for each pinned version, that is, every wheel (across platforms and Python versions) and the sdist. One lockfile therefore installs and verifies on any interpreter in range: on 3.13 pip consumes the matching wheel, on 3.14 (where a prebuilt wheel may or may not exist) pip consumes the matching wheel if present or builds from the hash-verified sdist. This was proven both ways: a clean Python 3.14 host install of requirements.txt and a Python 3.13 install of the same file inside the pinned base image both resolved and verified to the identical locked set.

`--require-hashes` is enforced in all three install paths: `.github/workflows/ci.yml` (the test job), `.github/workflows/quality.yml` (the ruff and mypy jobs), and `tools/Dockerfile.sandbox` (the image build now does `COPY requirements-sandbox.txt .` then `RUN pip install --no-cache-dir --require-hashes -r requirements-sandbox.txt`). No new binary is added to any build path; CI, the host, and the image all install with plain `pip --require-hashes`.

pyproject sync: `[project].dependencies` mirrors `requirements.in`'s direct list name-for-name and version-for-version. `httpx==0.28.1` was added there because it is a direct runtime pin (llm_client imports httpx directly) that had been present in requirements.txt but missing from the pyproject list; adding it is a sync correction, not an upgrade. The pyproject sync comment now names `requirements.in` as the direct-list source and `requirements.txt` as the generated, hash-locked closure. `requirements.txt` is now a generated artifact, not the hand-maintained source it used to be; the source is `requirements.in`.

Alternatives rejected:
- uv (uv pip compile / uv.lock) instead of pip-tools: rejected for this phase. uv is faster and capable, but pip-tools emits a plain `requirements.txt` that the unchanged `pip --require-hashes` consumes directly in every environment (CI runner, dev host, and the slim container that already has pip), so no new tool enters the install path. The container especially benefits: it installs with the pip it already ships, with no extra binary to fetch and trust. uv would either add a binary to the build path or require its own lock format and resolver. pip-tools is the smaller, more boring change that meets the goal; uv remains a reasonable future migration if compile speed or workspace features are wanted.
- A single combined lockfile for all environments: rejected. The sandbox image must contain only pytest and its closure (decision 0007, minimal attack surface inside the boundary); shipping the full runtime or dev closure into the container would enlarge it for no reason. The dev/CI environment needs ruff, mypy, and pytest-cov that neither the runtime nor the container needs. Three locks keep each environment to exactly its closure.
- Compiling on the dev host (3.14) rather than 3.13: rejected. The canonical environment is the CI and container version (3.13). `--generate-hashes` makes the 3.13-compiled lock install on 3.14 anyway (proven), so the host is not constrained by the compile interpreter.
- Hand-adding hashes or hand-editing the `.txt` files: rejected. Hashes and the transitive set are generated; hand-editing would drift from the resolver and is error-prone. The `.in` files are the only hand-edited inputs.

Consequences: A clean environment (host, CI runner, or container) resolves to the exact locked, hash-verified versions, and `pip --require-hashes` rejects any tampered or substituted artifact. The direct runtime surface is unchanged and was proven byte-identical to the prior requirements.txt. Honest note on the enforcement semantics, surfaced while proving the guard bites: because `--generate-hashes` lists every artifact's hash (a package has at least a wheel hash and an sdist hash), `pip --require-hashes` accepts an install when the artifact it actually consumes matches any one listed hash. Corrupting a single non-consumed hash is therefore tolerated by design (pip selects another valid artifact, for example building from the still-valid sdist when a wheel hash is altered); the guard bites, with the canonical "THESE PACKAGES DO NOT MATCH THE HASHES" error, when the consumed artifact matches none of the listed hashes. This is correct supply-chain behavior (any one valid, untampered artifact is sufficient), not a gap: a substituted or tampered artifact has a hash present in none of the listed entries and is rejected. The SBOM and the CI vulnerability scan are out of scope here and are P6.2.2; this phase delivers the reproducible, hash-verified lock that those build on. No source, test, sandbox-lockdown, scoring, generation, or evaluation logic changed.
