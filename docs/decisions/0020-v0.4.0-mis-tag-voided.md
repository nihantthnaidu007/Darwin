# 0020 v0.4.0 mis-tag voided: the v0.4 release is published as 0.4.1

Decision: The v0.4.0 tag is treated as a void mis-tag and the v0.4 milestone (resilience and operability) is published as 0.4.1. The v0.4.0 tag was mis-created on the M0 merge commit (4cff555): it is annotated "Darwin 0.4.0: Foundation and Guardrails" (the M0 milestone name), points at a commit whose own message says "version stays 0.3.0," and contains none of the v0.4 work (tools/llm_client.py, tools/runstate.py, tools/logsetup.py, tools/runinput.py). The tag is already pushed to origin. Per the never-force-push-tags rule (decision 0015), a published tag is never force-updated or deleted, so v0.4.0 is left exactly where it is and is recorded here as void: never a real release. The version moves to 0.4.1 in pyproject.toml, the README release lines and CHANGELOG are updated to 0.4.1, and 0.4.1 is tagged at its merge commit on main, after the merge and the post-merge audit. This supersedes the tagging paragraph of decision 0019.

Context: The root cause is plain: the M0 merge commit was given a v0.4.0 release tag it should never have received. M0 (foundation and guardrails) does not bump the version (it merged with "version stays 0.3.0"), so no release tag belonged on it, and a v0.4.0 tag in particular belongs only on the v0.4 work, which lives on branch v0.4-resilience and is not contained in commit 4cff555. The close-out's decision 0019 and CONTEXT both planned to "tag 0.4.0 at its merge commit on main, after the post-merge audit." That plan is now impossible: the v0.4.0 name is taken, points at the wrong commit with the wrong annotation, and decision 0015 forbids force-updating or deleting it. The standard yanked-release pattern resolves this cleanly: leave the bad tag in place, mark it void, and publish under the next patch number. The 0.x line rationale (decision 0005) is unchanged, so the release stays in the 0.x line as 0.4.1.

Alternatives rejected:
- Force-update or delete the v0.4.0 tag to point at the real v0.4 merge commit: rejected. It is already on origin, and decision 0015 forbids force-updating or deleting a published tag. Rewriting it would break anyone who already fetched it and would reopen the tag discipline that 0015 exists to protect.
- Reuse 0.4.0 as the release number without retagging: rejected. The 0.4.0 tag would still point at the M0 merge with the M0 annotation, so the published 0.4.0 tag and the 0.4.0 release would name two different commits. Releasing under a fresh number (0.4.1) keeps the tag and the release in one-to-one correspondence.
- Skip a decision record and just bump the number: rejected. The void tag is a permanent, public artifact left in place on purpose; without a recorded reason a future reader would read v0.4.0 as a real release and 0.4.1 as a hotfix on top of it, which is false.

Consequences: The first 0.4.x release is 0.4.1; there is no 0.4.0 release. The v0.4.0 tag remains on origin, pointing at the M0 merge commit, recorded here as void; it is not a release and is never reused. 0.4.1 is tagged at its merge commit on main after the post-merge audit, in one-to-one correspondence with the release. The tagging paragraph of decision 0019 is superseded by this record; the rest of 0019 (the version-bump rationale and the four v0.4 findings) stands. The never-force-push-tags rule (decision 0015) and the 0.x line rationale (decision 0005) are both unchanged. A future 0.5.0 follows the same clean pattern: bump in pyproject, update the README references and CHANGELOG, and tag at the merge commit on main.
