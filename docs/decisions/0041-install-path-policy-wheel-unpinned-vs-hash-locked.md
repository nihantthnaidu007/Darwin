# 0041 Install-path policy: hash-locked requirements.txt is the supported install; the pip install . wheel is unpinned convenience

Decision: Darwin has two install paths, and the documentation states plainly which is for what. The supported, reproducible install is the hash-locked `requirements.txt` installed with `--require-hashes` (pip-tools `--generate-hashes`, decision 0028): it pins the exact direct-plus-transitive closure and verifies every artifact by hash. The `pip install .` wheel (decision 0040) is a convenience path: it resolves `[project].dependencies` as version ranges from PyPI, NOT the hash-locked closure, so it is for quick trial use, not for reproducible or security-reviewed installs. Neither path publishes to PyPI.

Context: Decision 0028 established hash-locked lockfiles as Darwin's supply-chain posture: the host, CI, and sandbox-image dependency closures are compiled with `pip-compile --generate-hashes` and installed with `pip --require-hashes`, so a substituted or tampered package fails the install. v0.8 added a second way to install Darwin -- the `pip install .` wheel -- whose runtime requirements come from `[project].dependencies` in `pyproject.toml`. Those are declared as version pins/ranges that mirror `requirements.in` name-for-name, but a wheel install resolves them against PyPI at install time WITHOUT hashes; it does not and cannot use the `requirements.txt` `--require-hashes` closure. Left undocumented, that would silently degrade the supply-chain posture: a user could `pip install .` believing they had the same hardened install the project advertises, when in fact they resolved an unpinned, unverified closure. The policy makes the distinction explicit rather than letting it erode quietly.

Which is recommended for what: use the hash-locked `requirements.txt` with `--require-hashes` for CI, for any security review, and for reproducing results -- anywhere the exact, verified closure matters. Use `pip install .` to try Darwin quickly or to get the `darwin-*` console scripts on `PATH` without caring about an exact closure. The README "Install" section, the CHANGELOG 0.8.0 entry, and the `pyproject.toml` header all state this split.

Alternatives rejected:
- Make `pip install .` hash-locked too (pin hashes in `[project].dependencies`): rejected. `pyproject.toml` dependency specifiers do not carry per-artifact hashes the way a pip requirements file does; the hash-locked, `--require-hashes` closure is a generated lockfile, which is the right artifact for that guarantee. Conflating the two would misrepresent what a wheel install actually verifies.
- Drop the hash-locked lockfiles now that `pip install .` exists: rejected. That would discard decision 0028's supply-chain posture, which is the reproducible and security-reviewed install. The wheel is an addition, not a replacement.
- Leave the difference undocumented: rejected. An unpinned convenience install that looks like the hardened one is exactly the silent degradation this record exists to prevent. The posture is preserved only if the two paths are labeled.
- Publish the wheel to PyPI: rejected (decision 0040). Darwin stays GitHub-tagged and installed from a checkout.

Consequences: Decision 0028's hash-locked posture is intact and remains the supported, reproducible install. The `pip install .` wheel is documented as the convenience path that is NOT hash-locked, with the recommendation stated for each use. The supply-chain posture does not degrade silently, because the weaker path is labeled weaker wherever it appears. No engine, scoring, gate, generator, evaluator, or sandbox behavior changed; this record sets install-path policy and documentation, not code behavior.
