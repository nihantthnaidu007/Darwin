# 0019 v0.4 release: first roadmap version bump to 0.4.0, staying in the 0.x line

Decision: Bump the release version from 0.3.0 to 0.4.0 to record the v0.4 milestone (resilience and operability). This is the first version bump on the production-grade roadmap to 1.0; M0 (foundation and guardrails) was merged with no version bump, and v0.4 is the first milestone that bumps the release version because it ships substantive runtime behavior. The version moves to 0.4.0 and stays in the 0.x line, because the open boundaries from decision 0005 are not yet closed: a 1.0 would signal a stable, production-grade release with those boundaries closed, and Darwin is not there. The version lives in pyproject.toml; the two README release references and the package-metadata comments are updated to match, and CHANGELOG.md records the 0.4.0 and 0.3.0 entries.

Context: v0.4 closed four findings, with no change to the optimization, scoring, or equivalence behavior:
- B1, LLM-call resilience and resumable runs: hardened LLM calls (explicit timeout, bounded retries, a shared retryable-versus-fatal error taxonomy, model-capability fallback) plus resumable checkpointed runs that refuse a config-mismatched resume.
- B2, image preflight false-negative: an image preflight that tolerates the inspect-by-tag false negative via a listing fallback.
- E1, structured logging: structured logging across the core path with a readable console handler and a JSON handler, the RUN SUMMARY report preserved on stdout (decision 0018).
- N1, input and artifact validation: guarded JSON loading and case and mcase shape validation on the run-path readers, the simulated-attack payload exhibits left as authored.

Tagging: 0.4.0 will be tagged at its merge commit on main, after the merge and the post-merge audit, not on this close-out commit on the branch. This improves on the 0.3.0 tag drift accepted in decision 0015 (the v0.3.0 tag sits two no-op merge commits behind main): tagging 0.4.0 directly at its merge commit avoids opening a new tag-to-main gap. The never-force-push-tags rule from decision 0015 stands, so the existing v0.3.0 tag is left exactly where it is.

Consequences: 0.4.0 is the current honest 0.x release. The 0.x rationale (decision 0005) is unchanged: the version stays in the 0.x line until the open boundaries close, and 0.4.0 makes no benchmark-grade claim. The next milestone is v0.5 (correctness, determinism, and reproducibility): C1 the feedback-load-bearing contradiction, D1 module-global concurrency, F1 determinism and seeding, and N2 oracle sanitization. A future 0.5.0 bump follows the same pattern recorded here: bump in pyproject, update the README references and CHANGELOG, and tag at the merge commit on main.
