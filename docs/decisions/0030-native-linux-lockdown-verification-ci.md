# 0030 Native-Linux container-lockdown verification in CI (Option A)

Decision: Close the verifiable half of A4 by exercising the existing end-to-end container lockdown probe (`tools/verify_container_sandbox.py`) in CI across a matrix of native-Linux Ubuntu runners, recording the actual cgroup version, kernel, and Docker version each runner reports, and writing the native-Linux verification section of `SECURITY.md` scoped to exactly what ran. A new workflow `.github/workflows/isolation.yml` runs the probe on `ubuntu-22.04` and `ubuntu-24.04`; the probe's exit code gates each leg, so a lockdown breach (network reachable, the memory cap not firing, the fork bomb not contained, a leak, ...) fails CI. No lockdown flag in `sandbox_container.py` `_run_argv` was changed and no OOM detection logic was changed; the only code touched is a two-line non-behavioral comment in `_classify`.

Context: A4 had two halves. The lockdown itself was already enforced and already proven by `verify_container_sandbox.py` (network none, memory cap with swap disabled, CPU cap, PID cap, read-only root with an in-RAM `/tmp` tmpfs, cap-drop ALL, no-new-privileges, non-root uid 1000, single read-only bind mount, hard wall-clock timeout, clean teardown). The verifiable gap was that the probe is a standalone exit-0-or-1 script, NOT a `test_*.py` collected by the pytest suite that `ci.yml` runs, so the network/OOM/PID/read-only/timeout/teardown checks were never exercised in CI, and there was no native-Linux security writeup. SECURITY.md carried only a pre-CI caveat that the isolation was verified on macOS Docker Desktop and "not yet" on native Linux. This phase exercises the probe on native Linux in CI and writes the native-Linux section against the recorded evidence.

Option A (taken) versus Option B (deferred): Option A verifies the lockdown on the matrix the hosted runner fleet can actually provide (Ubuntu on cgroup v2) and documents cgroup v1 and non-Ubuntu distributions as an explicit self-hosted / VM follow-up. Option B would stand up self-hosted cgroup-v1 runners (or VMs on an alternate distribution) now to exercise v1 in CI. Option B is deferred: GitHub hosted runners are Ubuntu on cgroup v2, so a cgroup-v1 leg cannot be obtained from the hosted fleet at all; it requires provisioning and trusting self-hosted infrastructure, which is a larger change than verifying the achievable matrix. The version-dependent risk that v1 would probe is narrow (see "version-robust" below), so Option A closes the verifiable half now and names the v1/other-distro run as the documented follow-up rather than blocking on infrastructure.

The achievable matrix and the recorded evidence: The matrix is two Ubuntu versions for kernel and Docker variety. The run on commit `aa79249` (workflow run 27705388059) recorded, per leg (from `docker info --format '{{.CgroupVersion}}'`, `uname -r`, and `docker --version`):

- `ubuntu-22.04`: cgroup version 2, kernel `6.8.0-1052-azure`, Docker `28.0.4` (build b8034c0). Probe: all 9 guarantees held, exit 0.
- `ubuntu-24.04`: cgroup version 2, kernel `6.17.0-1018-azure`, Docker `28.0.4` (build b8034c0). Probe: all 9 guarantees held, exit 0.

Both legs are cgroup v2, as expected for the hosted Ubuntu fleet. On both legs the memory-flood check reported exit 137, status CRASHED, and `oom_killed=True` (the inspect OOM flag is set on cgroup v2 here), and the fork bomb was blocked after 127 children. The hashed install path from P6.2.1 is used (`pip install --require-hashes -r requirements-dev.txt`), and the image is built from the pinned Dockerfile (decision 0027).

The status classification is already version-robust, so no detection change was made: an OOM kill is a SIGKILL that Docker reports as exit 137, and `_classify` maps any exit code >= 128 to CRASHED whether or not `.State.OOMKilled` is set. The only version-dependent piece is the `oom_killed` boolean, which reads `.State.OOMKilled` in `_inspect`. The memory-cap ENFORCEMENT (the candidate is killed and classified CRASHED) therefore does not depend on the inspect flag at all. Because the classification was already correct across cgroup versions, this phase changed no detection logic. The only edit to `sandbox_container.py` is a two-line comment on the final `return CRASHED` in `_classify` noting that the exit >= 128 path already covers an OOM kill when the inspect flag is unset; it changes no behavior and the suite count is unaffected (209 passed, 2 xfailed before and after).

The evidence-gated flag contingency: the one case that would have required a real fix is the OOM check failing specifically because `.State.OOMKilled` is false on a real OOM (the cap still fired, exit 137, status CRASHED, but the flag is unset). Per the phase bar this would be stopped on and reported with the leg's raw output rather than masked, because there the flag, not the status, would need correcting. That contingency did NOT trigger: on both cgroup-v2 legs `oom_killed=True`. It is recorded here as the condition under which the `oom_killed` source would be revisited, so the contract is on the record even though it was not hit.

`isolation_audit.py` is deliberately NOT wired into this workflow. It is a cost/overhead and reward-hack instrument that wraps a real `loop.run_loop` or `benchmark.run_benchmark` (which call the LLM and so need an `ANTHROPIC_API_KEY` that CI intentionally does not have), and its only lockdown-adjacent guarantee, the cleanup-at-scale `leak_check`, is already covered by the probe's check `i` (no leaked containers or host temp artifacts). It adds no distinct lockdown guarantee not already exercised by the probe, so including it would add an API-key dependency and a forgery-corpus scan to CI for no additional lockdown coverage.

SECURITY.md scope, stated precisely: the native-Linux verification section records the two runner images, the cgroup version actually exercised (v2 on both), the kernels and the Docker version, and the guarantees the probe confirms (network isolation, host-filesystem isolation, memory cap enforced via OOM kill, PID cap, hard timeout, clean teardown, with read-only root, non-root uid 1000, cap-drop ALL, and no-new-privileges applied on every run and exercised under the full battery). It states plainly that the memory-cap enforcement is version-robust by construction, and it states plainly the limit: cgroup v1 and non-Ubuntu distributions are NOT exercised in CI because hosted runners are Ubuntu on cgroup v2, and a real v1 or alternate-distribution run is a documented self-hosted / VM follow-up. The section claims no coverage the matrix did not produce.

Out of scope (unchanged here): cgroup-v1 and non-Ubuntu CI testing (the documented follow-up above); any speculative OOM heuristic or change to how `oom_killed` is sourced; seccomp, user namespaces, and the verdict-emission seam (P6.4); the pytest CVE bump (deferred to P7.2, decision 0029); and scoring, generation, evaluation, or any `_run_argv` lockdown flag. This phase verifies the existing lockdown on native Linux and documents it; it does not change the lockdown.

Consequences: CI now exercises the full container lockdown on native Linux (Ubuntu, cgroup v2) on every push and on PRs to main, across two Ubuntu versions and two kernels, with the probe's exit code gating each leg. SECURITY.md no longer carries the "native Linux not yet verified" caveat; it carries a verification section scoped to the recorded matrix and an explicit statement of what is not covered. The remaining native-Linux gap is narrow and named: a cgroup-v1 or non-Ubuntu run on self-hosted infrastructure or a VM, which would exercise the one version-dependent piece (the `oom_killed` inspect flag), noting that the memory-cap enforcement is already version-robust regardless. No lockdown flag, no OOM detection logic, and no scoring/generation/evaluation behavior changed.
