# 0027 Base image pinned by manifest-list digest

Decision: The sandbox base image is pinned by digest. tools/Dockerfile.sandbox builds `FROM python:3.13-slim@sha256:<digest>` instead of the mutable `python:3.13-slim` tag, where `<digest>` is the multi-arch OCI image index (manifest list) digest. The digest value lives in exactly one place, the FROM line of tools/Dockerfile.sandbox, and is deliberately not repeated here or anywhere in the code, so there is nothing to keep in sync; this record describes the pin and how to rotate it, the Dockerfile holds the value. The digest is obtained from the registry with `docker buildx imagetools inspect python:3.13-slim --format '{{.Manifest.Digest}}'` (equivalently the top-level digest from `docker manifest inspect python:3.13-slim`), not a per-platform manifest digest. The locally built sandbox image `darwin-sandbox:py313` is deliberately NOT given a fixed committed digest; the sandbox reference in `run()` (sandbox_container.py) stays the local tag.

Context: A2 flagged that the Dockerfile built `FROM python:3.13-slim`, a mutable tag. The tag is republished as the upstream image changes (new patch releases, new Debian base), so two builds days apart could produce sandbox images on different bases, and the security boundary could change under us between builds without any change to our own files. Pinning the base by digest makes a rebuild pull the exact same base bytes: a digest is content-addressed, so the pinned `python:3.13-slim@sha256:<digest>` reference always resolves to the same image or fails closed if it is no longer served. The boundary is then reproducible by construction: the pinned base plus the committed Dockerfile fully determine the sandbox image's security-relevant content. `run()` resolves the local tag `darwin-sandbox:py313`, which is built from this Dockerfile, so it resolves to an image built from a fixed base. The manifest-list digest, rather than a per-platform digest, was chosen so the one FROM line is reproducible on both arm64 (the current dev host) and x86_64; the index digest resolves to the correct per-platform image on each architecture, while a per-platform digest would only build on the matching architecture and would force the FROM line to differ across hosts.

The reason the locally built sandbox image is not given a fixed committed digest: `darwin-sandbox:py313` is built on each host with `docker build`, so it has no fixed portable digest. The built image digest varies by host and by architecture (different base manifest selected, different build environment), so a hardcoded sandbox-image digest committed to the repo would break on a fresh clone and across architectures, and would be a second digest to keep in sync with the base pin. The boundary is instead made reproducible by the one input that is portable and content-addressed: the pinned base digest, combined with the committed Dockerfile. That is the single source the build derives from.

Verification performed at pin time: building from the pinned Dockerfile pulled the base by digest (the build log `FROM docker.io/library/python:3.13-slim@sha256:...` step reported `resolve ... done`); pulling the base by that digest returned the same image (all layers "Already exists"); and `docker image inspect python:3.13-slim@sha256:<digest> --format '{{json .RepoDigests}}'` reported exactly that digest. The full sandbox test suite (serial) passed unchanged, confirming the boundary behavior is identical to the unpinned base; this phase pins the base and documents reproducibility only, it does not change sandbox behavior.

Rotation procedure (when the base ships a security update worth taking): (1) fetch the current manifest-list digest with `docker buildx imagetools inspect python:3.13-slim --format '{{.Manifest.Digest}}'` (or `docker manifest inspect python:3.13-slim`, taking the top-level manifest-list digest, not a per-platform one); (2) replace only the digest on the FROM line in tools/Dockerfile.sandbox with the new value, nothing else changes; (3) rebuild the sandbox image from the pinned base with `docker build -f tools/Dockerfile.sandbox -t darwin-sandbox:py313 tools/`. The same procedure is recorded as a comment block at the top of tools/Dockerfile.sandbox so a maintainer editing the file finds it in place.

Alternatives rejected:
- Keep the mutable `python:3.13-slim` tag: rejected, this is exactly the A2 hazard. The boundary could change between builds with no change to our files, defeating reproducibility.
- Pin a per-platform (per-architecture) manifest digest: rejected. It would build only on the matching architecture and would force the FROM line to differ between the arm64 dev host and x86_64, breaking the single-line cross-arch reproducibility. The manifest-list (image index) digest resolves correctly on every architecture from one line.
- Commit a fixed digest for the locally built `darwin-sandbox:py313` image: rejected. The locally built image has no portable digest; a hardcoded one breaks on a fresh clone and across architectures, and adds a second digest to keep in sync. Reproducibility is anchored on the portable, content-addressed base digest plus the committed Dockerfile instead.
- Repeat the digest value in this decision record for the reader's convenience: rejected. A second copy of the literal digest is a second thing to keep in sync and would drift on rotation. The record points at the FROM line, which is the single source.
- Add a run-side base-digest provenance check now (the base-digest LABEL stamped into the image and verified at preflight in `run()`): deliberately deferred as a 2.0 / multi-tenant concern. In the single-user-trusted 1.0 the maintainer builds the image they run, so a preflight digest assertion guards against nothing the threat model includes, and it would reintroduce exactly the cross-file digest drift this pin avoids (a committed expected-digest in the code to keep in sync with the Dockerfile). It is recorded here as a future direction, to be added if and when the model becomes multi-tenant or the build and run hosts diverge.

Consequences: A rebuild of the sandbox image pulls the exact same base, so the security boundary is reproducible by construction from two committed inputs, the pinned base digest and the Dockerfile. The digest has a single home (the FROM line); the code and this record carry no copy, so there is nothing to keep in sync and decision 0007 (the container is the boundary) is strengthened, not changed. The sandbox lockdown, the IMAGE tag resolved by `run()`, timeouts, teardown, container naming, scoring, generation, and evaluation are all untouched. Honest residuals: the in-container `pip install pytest==8.3.5` is version-pinned but not yet hash-locked, and there is no SBOM or vulnerability scan; that is dependency-side supply-chain hardening, scoped to P6.2, not here. The deferred run-side provenance check above remains the documented follow-up for a multi-tenant 2.0.
