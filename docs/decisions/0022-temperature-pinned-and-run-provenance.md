# 0022 Temperature pinned to 1.0 and recorded as run provenance

Decision: The generators set temperature explicitly to 1.0 on every path, and the run record (run.json) gains a provenance block describing the exact request configuration: the effective temperature (1.0), the model id, the Anthropic SDK version, max_tokens, and the thinking decision (whether adaptive thinking and the effort knob were sent). Temperature is a single shared constant `generator.TEMPERATURE = 1.0`. The request kwargs and the provenance are built by one pair of helpers in generator.py (`request_kwargs` and `request_provenance`); mgenerator reuses `request_kwargs` and both loops record `request_provenance(model)`, so the recorded provenance is assembled from the same source the generator actually sends and cannot drift from it. The SDK version is read once from `anthropic.__version__` via `llm_client.sdk_version()`, never hardcoded.

Context: The generators set no temperature and the run record carried no request parameters, so a result could not be traced to its exact configuration and was needlessly non-reproducible on top of the irreducible model variance. The generators run adaptive thinking on capable models, and the Anthropic API constrains temperature to 1.0 when thinking is enabled; the prior unset default was also 1.0, which is what the committed variance data was generated under. The behavior-preserving, explicit value is therefore 1.0. Whether the adaptive-thinking path would accept an explicit `temperature=1.0` or require it omitted was determined empirically against claude-opus-4-8: an explicit `temperature=1.0` alongside `thinking={"type":"adaptive"}` and `output_config={"effort":"medium"}` was accepted and returned a normal completion. So temperature is set explicitly to 1.0 on both the thinking and the no-thinking path; the effective value is unchanged from the prior default, only now explicit and recorded. Bit-for-bit determinism is out of scope and impossible for an LLM; the goal is recorded, reproducible configuration so the only remaining variance is the model's own.

Alternatives rejected:
- Set temperature to 0: rejected. It would change optimization behavior, conflict with the adaptive-thinking path (which constrains temperature to 1.0), and invalidate the P5.3 variance finding, which was generated at the effective temperature of 1.0.
- Omit temperature on the adaptive-thinking path: rejected because unnecessary. The API accepts an explicit 1.0 there (verified), so sending it explicitly on both paths keeps the two paths uniform and makes the value recorded at the call site rather than implied by an API default. The effective value is identical either way; explicit is clearer and self-documenting. Had the probe shown the explicit value was rejected, this record would instead document omitting it on the thinking path while still recording the effective 1.0; the probe made that unnecessary.
- Hardcode the SDK version as a string in the run record: rejected. It would drift from the SDK that actually made the call. Reading `anthropic.__version__` records the real version.
- Re-type the temperature, max_tokens, and thinking config as literals in the loop when building run.json: rejected. Two copies can drift, so the loop reads the generator's own `request_provenance` and writes it verbatim; the provenance equals the request by construction.

Consequences: Results and the variance finding are unchanged, because the effective temperature (1.0) is exactly what runs used before. Every run.json now self-describes the configuration that produced it: temperature, model, SDK version, max_tokens, and the thinking decision. The provenance block is additive; the existing fields and the summary readers (run_summary, mrun_summary) are untouched. A future change to the temperature floor, the model, the token budget, or the SDK is recorded automatically in each run rather than living only in code. Bit-for-bit determinism remains explicitly out of scope. The checkpoint config-mismatch guard (decision 0017) is unchanged: temperature is always 1.0, so it does not enter the resume-mismatch check.
