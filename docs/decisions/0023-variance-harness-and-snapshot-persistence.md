# 0023 Variance harness and snapshot persistence

Decision: The multi-file run-to-run variance dataset (reports/mvariance.json) becomes reproducible from retained artifacts rather than hand-recorded numbers. A harness, tools/variance_harness.py, has two modes. `derive` reads every maggregate.json snapshot under a snapshot directory (default reports/variance_runs) and computes the mvariance dataset: per case the arrays across runs of best_generation, gen1_bloat_removed_pct, feedback_gain_pp, and best_bloat_removed_pct, the per-case one_shot_runs and needed_feedback_runs counts, and the computable summary facts (improved-over-baseline and regression counts, the generation-1 and feedback-gain ranges, and how many runs were all-cases-one-shot). `run` orchestrates N multi-file benchmark runs, each writing its maggregate.json to a distinct committed snapshot path under reports/variance_runs via mbenchmark's existing --out, then calls derive. Snapshots are persisted under the committable reports/variance_runs directory, which the README scaffolds. The derive output is deterministic and order-stable (snapshots sorted by path, case keys sorted), so a rerun on the same snapshots is byte-identical. This phase (P5.3a) builds and unit-tests the machinery on synthetic snapshot fixtures and a stubbed runner, spends nothing, and changes no committed variance number; only mvariance.json's note is updated to record that the harness exists. The authorized runs that populate reports/variance_runs with real snapshots are P5.3b.

Context: reports/mvariance.json's six rows were hand-recorded from the printed mbenchmark.py output. Only the most recent run was independently corroborable from the gitignored on-disk maggregate.json; the other five rows had no retained artifact, so the variance result could not be regenerated. The fix is to persist each run's aggregate as a committed snapshot and derive the dataset from those snapshots. mbenchmark.py already writes a complete maggregate.json to a directory given by --out, so the harness needs no change to mbenchmark: it points each run at a distinct snapshot directory and then reads them back. The derive logic renames two per-case fields to the mvariance field names, since the snapshot and the mvariance dataset name the same quantity differently: each snapshot's first_pass_bloat_removed_pct maps to gen1_bloat_removed_pct (generation 1 alone), and each snapshot's cases[] bloat_removed_pct maps to best_bloat_removed_pct (the returned best). best_generation and feedback_gain_pp keep their names. Reading the real snapshot field names is what lets derive consume the actual maggregate.json that P5.3b will emit.

Alternatives rejected:
- A fixed random seed for bit-for-bit reproducibility: rejected. The generator is a stochastic LLM at temperature 1.0 (pinned in decision 0022 to preserve this very variance finding), so its output is not bit-deterministic and no seed makes it so. Reproducibility here means a retained, re-derivable dataset, not a deterministic model, which is what committed snapshots plus a deterministic derive provide.
- Regenerate the committed mvariance numbers now: rejected and out of scope. It would require running the model (spend) and would change committed numbers; P5.3a is machinery-only. The numbers stay the 2026-06-13 hand-recorded dataset until P5.3b populates the snapshots, at which point derive regenerates them from artifacts.
- Modify mbenchmark.py to emit the variance dataset directly: rejected. mbenchmark aggregates one run; the variance dataset is across runs. Keeping mbenchmark unchanged and adding a thin harness that reuses its --out keeps the one-run aggregator and the across-run derivation separate and leaves the scoring path untouched.

Consequences: reports/variance_runs is a committable home for per-run snapshots, scaffolded with a README that documents the two-step reproduction. The reproduction procedure is: `python variance_harness.py run --n 6 ...` (the authorized P5.3b spend that runs the model and writes the snapshots), then `python variance_harness.py derive` (no spend, deterministic, byte-identical on rerun). The derive path is proven on synthetic snapshot fixtures and the run orchestration on a stubbed runner, both with zero API calls. mbenchmark.py, the scoring, evaluation, sandbox, generation, and feedback logic are untouched. The committed mvariance numbers remain hand-recorded until P5.3b; only the note now reflects that the harness exists.
