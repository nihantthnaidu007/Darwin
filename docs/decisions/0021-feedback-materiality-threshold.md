# 0021 Feedback load-bearing has a materiality threshold

Decision: The aggregate field `feedback_load_bearing` is true only when at least one needed-feedback case improved on its first scored generation by a margin that clears a materiality floor, not merely when some case used a later generation at all. The floor is a single shared constant, `FEEDBACK_MATERIALITY_EPSILON_PP = 0.5` (percentage points), defined once in tools/feedback_materiality.py and referenced by both tools/benchmark.py and tools/mbenchmark.py. The exact comparison is `any(c["feedback_gain_pp"] > FEEDBACK_MATERIALITY_EPSILON_PP for c in needed_feedback)`: strictly greater than 0.5 pp, so a gain at or below 0.5 pp does not make the field true. On the committed single-file data the two needed-feedback cases gained 0.37 pp (format_duration) and 0.40 pp (int_to_words), both at or below the floor, so the field is false.

Context: The field was `bool(needed_feedback)`, true whenever any improved case reached its best at generation 2 or later, regardless of how little the later generation added. The committed reports/aggregate.json therefore read `feedback_load_bearing: true` while the README and reports/RESULTS.md state, with the per-case magnitudes, that the loop is not load-bearing on this corpus and that the two gen-2 bests added only a fraction of a percentage point. The boolean overpromised relative to its name: a machine reading the JSON reached the opposite conclusion from the human reading the report. A gain of a few tenths of a percentage point on top of a first pass that already removed over 99 percent of the bloat is within LLM run-to-run noise (the same instability documented for the multi-file scope in decision 0014); it is not evidence that the directed loop did real work. This record makes the boolean agree with the prose by gating it on magnitude, the same magnitude the needed_feedback_cases entries already carry as feedback_gain_pp. The list of needed_feedback_cases is unchanged: it is a factual record of which cases used a later generation, and which cases used feedback is a different question from whether feedback was load-bearing.

Alternatives rejected:
- Leave the field as `bool(needed_feedback)` and explain the gap in prose: rejected. The artifact is the machine-readable claim; a reader parsing the JSON would still get the wrong answer, and the documented finding (decision 0006, the one-shot finding) is that the loop is not load-bearing at this scope.
- Drop the field or replace it with the raw gains: rejected. Downstream readers want the single yes-or-no the report headline gives; the gains are already present per case, so the boolean should summarize them honestly rather than be removed.
- Inline the 0.5 literal in both orchestrators: rejected. Two copies can drift, which would let the single-file and multi-file paths disagree on what "material" means. One shared constant keeps a future change to the floor in one place.

Consequences: `feedback_load_bearing` now answers "did feedback do material work," not "did any case use a later generation." On the committed single-file data it is false, matching the README and RESULTS prose and decision 0006. The needed_feedback_cases list and every other aggregate field are unchanged; the only edit to the committed reports/aggregate.json is the one boolean, recomputed from the existing committed gains with no benchmark re-run. The same constant and comparison are applied in mbenchmark.py for code consistency; there is no committed maggregate.json, so nothing is regenerated on the multi-file side. A future change to the materiality floor is a one-line edit to FEEDBACK_MATERIALITY_EPSILON_PP and takes effect in both paths at once.
