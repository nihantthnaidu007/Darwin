# 0039 v0.7 release: bump to 0.7.0

Decision: The v0.7 milestone (test and CI maturity) is released as 0.7.0. The version moves from 0.6.0 to 0.7.0 in pyproject.toml; the README release lines, CHANGELOG, and CONTEXT are updated to 0.7.0; and 0.7.0 is tagged at its merge commit on main, after the merge and the post-merge audit. The release stays in the 0.x line: the open boundaries from decision 0005 (most prominently the in-process verdict-forgery residual, decision 0008) are unchanged in v0.7, so this is not a 1.0. No optimization, scoring, equivalence, or default-lockdown behavior changed in v0.7; the milestone hardened the test and CI surface.

Context: v0.7 set out to mature the test and CI surface and to close the dependency-CVE coupling carried out of v0.6. The work, all audited across P7.1 through P7.5:

- P7.1/P7.2: the deferred pytest 8.3.5 to 9.0.3 bump cleared CVE-2025-71176 (the v0.6 advisory pip-audit finding), with the three hash-locked closures recompiled on the canonical Python 3.13, pulling pygments in as a new transitive of pytest (decision 0036).
- P7.2: direct unit tests for the loop orchestrator (`loop.py`: never-worse-than-baseline fallback, the generation cap, plateau stop) and the single-function verifier (`verify_case.py`: Layer 1 then Layer 2 gate ordering, the withheld oracle, the failing-gate taxonomy), bringing both to 99 percent line coverage.
- P7.3/P7.4: the four quality gates (ruff lint and format, mypy, gitleaks) plus the pip-audit dependency scan driven to zero findings and flipped from advisory to blocking, and a `--cov-fail-under=56` coverage floor set from production coverage measured at 58 percent less a 2-point margin (decision 0037).
- P7.5: a Python 3.12/3.13/3.14 host CI matrix (`fail-fast: false`) validated against the single hashed dev lock, with the lock confirmed to install under `--require-hashes` on 3.12 Linux, 3.13 Linux CI, and 3.14 macOS, so no per-version locks were added (decision 0038).

The v0.6.1 tag deletion, recorded plainly: during the P5.3b merge (the authorized variance regeneration that closed v0.5's F1, decision 0035), a `v0.6.1` tag was briefly pushed to origin in error and then removed. Deleting a published tag deviates from the never-force-push-or-delete-tags rule (decisions 0005 and 0015). This was a deliberate operator action, recorded here rather than hidden, in keeping with the project's honesty-over-tidiness posture. P5.3b carries no tag by design: it changed no version (it regenerated a data artifact), so no release tag belongs on it. This case is distinct from the v0.4.0 mis-tag (decision 0020), which was left void in place because decision 0015 forbids deleting a published tag; v0.6.1 was deleted, not left in place. The deviation is noted so a future reader does not infer a consistent never-delete history that the v0.6.1 deletion breaks.

Alternatives rejected:
- Release as 1.0 or leave the 0.x line: rejected. The open boundaries from decision 0005 are unchanged in v0.7 (A1 is still open by design); a 1.0 would falsely signal a stable, production-grade, forgery-proof release. The 0.x rationale stands.
- Bump only the patch (0.6.1): rejected on two grounds. First, v0.7 is a coherent milestone (a CVE clear, new orchestration-core tests, the advisory-to-blocking gate flip, a coverage floor, and a host-Python matrix), which is a minor bump, parallel to how v0.4, v0.5, and v0.6 were minor bumps. Second, the 0.6.1 name is now entangled with the deleted-in-error tag above; reusing it as a real release would invite confusion with that deletion. 0.7.0 is the clean, honest number.
- Tag P5.3b retroactively to regularize the deleted v0.6.1: rejected. P5.3b changed no version and merits no release tag; inventing one to paper over the deletion would compound the original error. The honest record is that the tag was pushed in error and removed, and P5.3b stays untagged.

Consequences: The current release is 0.7.0, tagged at its merge commit on main after the post-merge audit, in one-to-one correspondence with the release. The prior releases (0.6.0, 0.5.0, 0.4.1) and the void v0.4.0 tag are unchanged (decisions 0034, 0026, 0019, 0020). The release stays 0.x per decision 0005. The decision range is now complete through 0039 except for the intentionally skipped 0031 (decision 0034); following the never-renumber discipline (decisions 0015, 0020), the 0031 gap is left in place and not backfilled. No optimization, scoring, equivalence, or default-lockdown behavior changed in v0.7; the suite is steady at 257 passed, 2 xfailed, plus one Docker-gated skip when the daemon is absent. The merge to main and the 0.7.0 tag are the next package after this close-out is verified and pushed.
