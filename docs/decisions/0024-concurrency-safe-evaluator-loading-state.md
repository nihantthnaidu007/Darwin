# 0024 Concurrency-safe evaluator loading state

Decision: The evaluator's dynamic-import loading state is made concurrency-safe by minting each loaded module's name from a uuid instead of a module-global counter. Three loaders did this with a module-global counter: mverify._load_corpus, validate_mcase._load_module, and mdiffer.load_unit, which named their dynamically imported module `mverify_corpus_{_LOAD}` / `mcase_aux_{_LOAD}` / `mcase_unit_{_LOAD_COUNT}`, where the counter (`_LOAD`, or `_LOAD_COUNT` in mdiffer) was a module-global integer incremented with a non-atomic `global ...; ... += 1`. That increment is a non-atomic read-modify-write on shared state, so two concurrent loads could read the same counter, mint the same name, and collide on a sys.modules entry. The counter globals and their `global` statements are removed; each load now names its module `mverify_corpus_{uuid4().hex}` / `mcase_aux_{uuid4().hex}` / `mcase_unit_{uuid4().hex}`, which is collision-free without any coordination. uuid is standard library and is already the uniqueness pattern in sandbox_container.py. The module is still registered in sys.modules under its unique name, so load behavior is otherwise unchanged. The container execution path is confirmed safe by construction and not modified: sandbox_container.run gives each run a uuid-unique container name (`"darwin_sbx_" + uuid.uuid4().hex`, passed to `docker run --name`) and a fresh per-run host working directory (`tempfile.mkdtemp`), plus fresh `tempfile.mkstemp` output files, so two concurrent container evaluations cannot collide on a name or a directory. Production evaluation nonetheless still runs sequentially, one candidate per call; this phase makes the state safe to parallelize, it does not parallelize it.

Context: D1 identified the module-global load counters as the concrete reason the mevaluator docstring gave for keeping evaluation sequential: the load counter was unsafe under concurrent use. The non-atomic increment is a real race, demonstrated directly: 64 concurrent loads through the old shared-counter scheme minted only 48 distinct names (16 collisions), while the uuid scheme minted 64 distinct names. A collision means two loads register the same sys.modules key, so one clobbers the other, which is exactly the hazard that blocked any future parallel candidate evaluation. An initial pass converted mverify._load_corpus and validate_mcase._load_module but scoped its inventory grep to a hand-picked file list rather than the real import closure, and so missed mdiffer._LOAD_COUNT, a third counter reached host-side on the evaluation path via mdiffer.load_unit at mverify.check_equivalence_containerized (called from mevaluator.evaluate). Re-establishing the inventory by import closure caught it, and mdiffer.load_unit is converted the same way. The scoring, gate, and comparison logic are untouched; only the module-naming mechanism changes, so a loaded corpus, aux module, or host-side original unit behaves exactly as before. The reproduction is captured in tools/test_concurrency.py, which loads many distinct modules concurrently through each converted loader (threads released together by a barrier to maximize overlap on the minting) and asserts no name collision, no exception, and each load correct and independent.

Alternatives rejected:
- A thread-local or an atomic counter (for example itertools.count or a lock around the increment): rejected. The acceptance forbids a module-global mutable counter on the evaluation path, and a coordination-free uuid is simpler than any shared-but-synchronized counter, needs no lock, and matches the existing sandbox_container uniqueness pattern. A lock would also reintroduce shared mutable state, the thing being removed.
- Parallelizing production evaluation now: rejected and out of scope. This phase only makes the loading state safe and documents the guarantee; the real loop stays sequential. Activating parallel candidate evaluation is a later phase that now has a safe foundation.
- Cleaning up the slow accumulation of loaded-module entries in sys.modules: rejected as out of scope. The existing register-in-sys.modules behavior is preserved exactly; only the name changes from counter-based to uuid-based. The accumulation, if it matters, is a separate later item.

Consequences: The evaluator's loading state is concurrency-safe, removing the documented blocker to future parallelization without enabling it here. mverify.py, validate_mcase.py, and mdiffer.py carry no module-global mutable counter. This completeness claim is re-established by import closure, not a file list: walking the actual import closure of mevaluator.evaluate (evaluator, freeze_metrics, logsetup, mcase_metrics, mdiffer, mverify, runinput, sandbox_container, verify_case) shows no `global` statement and no module-level mutable counter or accumulator remaining on that path. The remaining named module-level state on the path -- mverify._BATCH_BUDGET, mverify._ABSENT, verify_case._LABEL, and the scoring constants such as evaluator.WEIGHTS -- is genuinely read-only, never reassigned or mutated, and is safe as-is. (The off-path module-level accumulators `_results` in verify_boundary.py and verify_container_sandbox.py are standalone verification scripts, not in this closure.) The mevaluator.py module docstring now states the concurrency-safety guarantee and that production stays sequential. sandbox_container.py, the container lockdown, timeouts, and teardown are unchanged. The sys.modules registration semantics are unchanged; the loaded-module accumulation remains a later item.
