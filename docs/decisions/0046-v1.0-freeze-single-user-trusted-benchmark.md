# 0046 v1.0 freeze: tag 1.0 as a single-user-trusted reproducible benchmark

Decision: Darwin is frozen and released as 1.0.0, a single-user-trusted, reproducible research benchmark and engine (framing (b)). The version moves from 0.9.0 to 1.0.0 in pyproject.toml (the single source of truth); the README version line and release line, the CHANGELOG, and SECURITY.md are reconciled to the 1.0 posture; and 1.0.0 is tagged at its merge commit on main after the merge and the post-merge audit. This is a documentation, version-metadata, and one-new-authoring-doc release: the version bump is the only non-doc change. No optimization, scoring, equivalence, gate, build_case, dataset, or case behavior changed in the freeze.

This reframes decision 0005. Decision 0005 originally reserved 1.0 until the open boundaries closed, naming the in-process verdict-forgery residual, native-Linux isolation, and a real benchmark. Two of those three are now closed: native-Linux isolation is CI-verified (decision 0030) and the benchmark exists (the v0.9 corpus and the authoritative one-shot finding, decisions 0043 through 0045). The third, the in-process verdict-forgery residual, is NOT closed; it remains open by design and is deferred to 2.0 (decision 0008). 1.0 therefore does not satisfy decision 0005's original all-boundaries-closed criterion. It is released under a different, explicitly stated framing: a single-user-trusted benchmark, where forging one's own optimization verdict is pointless and the reward-hack audits found the optimizer never approaches the forgery surface, so the open residual is a non-issue for the actual use case. Closing the forgery residual (framing (a): trusting the verdict on adversarial or third-party code) is 2.0 work and requires splitting the trusted emitter out of the candidate process, for which the VerdictEmitter seam is already in place (decision 0032). The honest position is that 1.0 commits to reproducibility and single-user trust, not to adversarial-code safety.

Context: v0.9 converted the one-shot finding from a 5-case anecdote into a grounded result (143 of 150 runs, 95.3 percent one-shot, on a 30-case synthetic single-function corpus run under one frozen config; reports/RESULTS.md, reports/v0.9-dataset.json; decision 0045). The engine has been stable since the v0.8 packaging close-out, with no optimization, scoring, equivalence, or default-lockdown change across v0.9 or this freeze. A pre-1.0 readiness audit found four classes of polish gap, all cleared in this freeze:

- The native-Linux SECURITY.md writeup was described in the README as still outstanding in three prose locations and one roadmap item, when it is in fact done (the native-Linux section of SECURITY.md, decision 0030). The README now states it as done and keeps only the genuinely-open part (cgroup v1, non-Ubuntu distributions, and a kernel-hardening audit, none of which the ubuntu-22.04 plus ubuntu-24.04 cgroup-v2 matrix exercises).
- The multi-file variance-snapshot retention was described in the README as a recorded follow-up item (hand-recorded rows, only the most recent run corroborable), when it is in fact done: all six runs are retained as committed snapshots under reports/variance_runs/run_00 through run_05, and reports/mvariance.json and reports/MRESULTS.md are byte-identically re-derivable from them (decision 0035). The README prose and the roadmap item are reconciled.
- The CI suite count was stale at 263 passed; the measured count is 331 passed, 2 xfailed, out of 333 collected (the Docker-gated seccomp smoke test skips when the sandbox image is not yet built).
- Cosmetic: the CONTEXT future-tense tag line (v0.9.0 is tagged now) and the SECURITY.md title, which carried a "(v2.0)" label that, at a 1.0 release, read as if the project were at v2.0 and had therefore closed the forgery boundary. The title now reads as the 1.0 single-user-trusted posture, with a numbering note disambiguating the access-isolation boundary generation (labeled v2.0 in that document) from the Darwin release line.

The stable-surface declaration (the 1.0 compatibility boundary): 1.0 commits to a CLI-and-file-format surface, not to an importable Python API. The stable surface is exactly three things: (1) the six console scripts (darwin-loop, darwin-mloop, darwin-benchmark, darwin-mbenchmark, darwin-variance, darwin-isolation-audit); (2) the case directory format (cases/<id>/ and mcases/<id>/ layout, plus the seed inputs reference.py, test_suite.py, spec.json now documented in docs/authoring-a-case.md); and (3) the dataset JSON schema (the committed result and case artifacts such as reports/v0.9-dataset.json, reports/mvariance.json, spec.json, golden_io.json, meta.json). Internal modules under src/darwin/ are importable but carry NO import-stability guarantee: module names, signatures, and internal structure may change within the 1.x line. Consumers depend on the CLIs and the file formats, not on importing darwin.<internal>.

This boundary is implemented as a documented statement, not as code. A package-level __all__ was considered and rejected: __all__ governs only `from darwin import *`, not `import darwin.<submodule>`, so it cannot prevent or even signal that submodule imports are unsupported. Declaring it would misstate the contract (it would imply a curated importable API that 1.0 deliberately does not offer) while doing nothing to constrain the actual import surface. The honest expression of "no import-stability guarantee" is the documented boundary in the README, so no code changed for the API decision.

Externally extendable benchmark: the one substantive reproducibility gap for framing (b) was that an external author could not add a case without reading build_case.py. docs/authoring-a-case.md closes that. It specifies the seed inputs, the spec.json schema field by field (category constrained to the seven, difficulty, entry_point, description, and arg_sets as the value-returning golden inputs, with raising inputs going in test_suite.py via pytest.raises because the golden recorder captures return values not exceptions), the reference-authoring rubric from the methodology contract (clean, idiomatic, pure, stdlib-only, authored to the rubric not to a one-shot target), and the build command. It is verified against the shipped seeds/roman_to_int/ seed, including a dry run of `python -m darwin.build_case seeds/roman_to_int` that refuses (the case already exists) before any LLM or Docker work, confirming the documented schema parses.

Alternatives rejected:
- Stay in the 0.x line: rejected. v0.9 delivered the grounded benchmark finding and the engine is stable; two of decision 0005's three boundaries are closed and the third is a non-issue under the stated single-user-trusted framing. Withholding 1.0 indefinitely on a residual that does not bite the actual use case would understate a finished, reproducible benchmark. The honest move is to tag 1.0 under framing (b) and state plainly what it does not cover.
- Tag 1.0 as production-grade or forgery-closed (framing (a)): rejected and explicitly disclaimed. The in-process forgery boundary is open by design (decision 0008); 1.0 is not safe to run on untrusted code with a trusted verdict. Implying otherwise would be the exact overclaim decision 0005 guarded against.
- Declare a curated importable API with __all__: rejected. It would misstate the contract (see above) and lock the project into stabilizing 22-plus internal modules it has no reason to freeze. The documented CLI-and-file-format surface is the smaller, honest commitment.
- Refresh CONTEXT.md fully to 1.0 in this prompt: out of scope. The prompt scoped only the cosmetic future-tense tag line in CONTEXT; the full CONTEXT version and decision-high-water refresh belongs to the post-1.0 CONTEXT close-out and is recorded as a non-blocking follow-up rather than churned here.

Consequences: The current release is 1.0.0, the single source of truth being pyproject.toml ([project].version, confirmed via importlib.metadata.version("darwin") returning 1.0.0). 1.0 commits to the CLI, case-directory, and dataset-schema surface, and explicitly does not commit to importable internals or to adversarial-code safety. The in-process verdict-forgery boundary stays open by design and deferred to 2.0 (decisions 0008, 0032); framing (a) is 2.0 work. The prior releases (0.9.0 back through 0.4.1) and the void v0.4.0 tag are unchanged. The decision range is now complete through 0046 except for the intentionally skipped 0031 (decision 0034); following the never-renumber discipline (decisions 0015, 0020), the 0031 gap is left in place. No optimization, scoring, equivalence, gate, build_case, dataset, or case behavior changed in the freeze; the suite is steady at 331 passed, 2 xfailed, out of 333 collected. The merge to main and the 1.0.0 tag are the next package after this close-out is verified and pushed.
