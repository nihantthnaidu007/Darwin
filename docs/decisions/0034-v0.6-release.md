# 0034 v0.6 release: bump to 0.6.0

Decision: The v0.6 milestone (supply-chain and isolation hardening) is released as 0.6.0. The version moves from 0.5.0 to 0.6.0 in pyproject.toml; the README release lines and CHANGELOG are updated to 0.6.0; and 0.6.0 is tagged at its merge commit on main, after the merge and the post-merge audit. The release stays in the 0.x line: the open boundaries from decision 0005 (most prominently the in-process verdict-forgery residual, decision 0008) are not yet closed, so this is not a 1.0. No optimization, scoring, equivalence, or default-lockdown behavior changed in v0.6; the milestone hardened the supply chain and the isolation boundary and built the forward-commitment seam for a 2.0 out-of-process emitter.

Context: v0.6 set out to harden the supply chain and the isolation boundary against the findings A2, G2, A4, and A3, and to prepare the seam that a multi-tenant 2.0 needs. The findings closed:

- A2 (reproducible image boundary): the sandbox base image is pinned by its multi-arch manifest-list digest rather than the mutable `python:3.13-slim` tag, with a documented rotation procedure, so a rebuild pulls the exact same base (P6.1, decision 0027).
- A2/G2 (dependency reproducibility and auditability): hash-locked lockfiles (pip-tools, `--generate-hashes`) for the host, CI, and the sandbox image, installed everywhere with `--require-hashes` (P6.2.1, decision 0028); a CycloneDX SBOM of the runtime surface uploaded as a CI build artifact; and an advisory pip-audit dependency vulnerability scan in CI (P6.2.2, decision 0029).
- A4 (native-Linux isolation verification): a CI matrix (`.github/workflows/isolation.yml`) exercises the container lockdown probe across two Ubuntu runners (ubuntu-22.04 and ubuntu-24.04) on cgroup v2, recording each runner's actual cgroup version, kernel, and Docker version, with the probe's exit code gating each leg, and a native-Linux section in SECURITY.md scoped to exactly that recorded evidence (P6.3, decision 0030).
- A3 (defense-in-depth and the forward-commitment seam): opt-in, off-by-default plumbing to append extra container `--security-opt` entries (a seccomp profile and related hardening), with the default `docker run` argv byte-identical when unset, an example starting-point seccomp profile (a labeled starting point, not a validated production profile), and the multi-tenant hardening posture documented in SECURITY.md (P6.4.1, decision 0033); plus a typed `VerdictEmitter` seam with an in-process default and a serializable verdict, with the multi-file consumers retyped to it so the 2.0 out-of-process emitter swaps in by replacing one component (P6.4.2, decision 0032).

A1, open by design at 1.0, now with the seam in place: in-process verdict forgery (the candidate and the trusted result-emitter share one process inside the container) stays open at 1.0. It is a non-issue under the single-user-trusted posture (forging one's own optimization verdict is pointless), is pinned by the two decision-0008 xfail vectors in `tools/test_behavior_gate_limits.py`, and is now backed by the `VerdictEmitter` seam (decision 0032) that the 2.0 out-of-process emitter drops into to close the forgery surface. Closing A1 itself, and validating a production seccomp profile and enabling daemon-level user-namespace remapping, are 2.0 multi-tenant work, documented and deferred.

Carried P6.3 documentation correction: decision 0030 and the `isolation.yml` comment described the CI matrix as covering "two Docker versions"; the recorded evidence is that both legs ran Docker 28.0.4, so the matrix covers two Ubuntu runners and two kernels but one Docker version. SECURITY.md already stated this correctly. This close-out corrects 0030 and the workflow comment to match the recorded evidence; it is a wording correction only, changing no code, test, or behavior.

Deferred, recorded honestly: the advisory pip-audit scan surfaced pytest CVE-2025-71176, present in the runtime and sandbox closures. The pytest 9 bump is out of scope for v0.6 (it is a dependency and major-version change) and is deferred to P7.2 (v0.7), where the bump must land before or together with the scan's flip from advisory to blocking, so the gate never flips to blocking on a finding the bump would clear.

Alternatives rejected:
- Release as 1.0 or leave the 0.x line: rejected. The open boundaries from decision 0005 are unchanged in v0.6 (A1 is still open by design); a 1.0 would falsely signal a stable, production-grade, forgery-proof release. The 0.x rationale stands.
- Bump only the patch (0.5.1): rejected. v0.6 closes three findings (A2, G2, A4) and delivers a fourth (A3) across the image boundary, the dependency surface, native-Linux verification, and defense-in-depth plus the forward-commitment seam; a minor bump (0.6.0) is the honest signal, parallel to how v0.4 and v0.5 were minor bumps.
- Bump pytest in this close-out to clear the CVE: rejected. The bump is a dependency and major-version change with its own validation, out of scope for a docs-and-version close-out; it is deferred to P7.2 with the blocking-flip coupling recorded above.

Consequences: The current release is 0.6.0, tagged at its merge commit on main after the post-merge audit, in one-to-one correspondence with the release. The prior release 0.5.0, the 0.4.1 release, and the void v0.4.0 tag are unchanged (decisions 0026, 0019, 0020); 0.5.0 and 0.4.1 references in CHANGELOG, the decision records, and CONTEXT history remain as intentional history. The release stays 0.x per decision 0005. No optimization, scoring, equivalence, default-lockdown, or seam behavior changed in this close-out; the suite is unchanged at 224 passed, 2 xfailed. The next milestone is v0.7 (test and CI maturity), which carries the deferred pytest 9 bump and the advisory-to-blocking flip of the quality and vulnerability gates (P7.2).
