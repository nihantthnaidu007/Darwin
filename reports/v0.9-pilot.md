# Darwin v0.9 Corpus Expansion: Synthetic Pilot Validation (P9.3)

Status: COMPLETE. This report validates the synthetic reference-first methodology
(docs/darwin-v0.9-corpus-methodology-synthetic.md) on 3 cases before the remaining
references are authored. It records the build-time spans, the temporal freeze, the
15 validation runs, the measured cost, and a three-point go/no-go assessment with a
recommended verdict.

All numbers below are reproducible from committed artifacts (the three cases under
cases/) and from the run.json files written under runs/ during the pilot. No engine,
scoring, gate, or build_case.py code was changed. This phase builds cases and runs the
existing engine; it writes no production code.

---

## 0. What the pilot did, and the one disclosed construction choice

The pilot builds 3 cases through the existing build_case.py path (record golden from
the clean reference, bloat the reference into the original via the LLM, gate the
original on pytest AND golden-I/O replay inside the container, freeze metrics, assemble
the case), commits them before running (temporal freeze), runs each 5 times under one
fixed loop configuration, and measures.

Disclosed construction choice (P9.3 decision): the 3 pilot references are byte-identical
copies of three already-authored corpus references (sum_evens, merge_intervals,
income_tax), rebuilt under new case_ids (pilot_sum_evens, pilot_merge_intervals,
pilot_income_tax) so the existing 5-case corpus stays intact and nothing is overwritten.
No reference was authored or altered for the pilot. The reference files were copied
verbatim (sha-256 prefix verified identical to source) and only the case_id field in
each spec.json copy was set to the pilot name.

What this choice means for the validation is stated plainly in Section 6 (Scope of the
finding): the pilot validates the full toolchain and the engine behavior end to end on
real, substantial-span single-function cases, but because the references are reused it
does not independently exercise the one part of the methodology that the full build adds,
which is a human authoring a fresh reference. The cost and coherence findings are
properties of the engine and carry forward; the generation-count finding on these three
is consistent with the existing RESULTS.md rather than independent new evidence.

## 4. Cost: total and per-run, versus the estimate

```
total measured spend (15 runs) = $0.158550
per-run average                = $0.010570
tokens (in / out)              = 20895 / 2163
estimate (methodology Sec 5)   = $0.03 per single-function case per run
ratio (per-run avg / estimate) = 0.35x
```

The per-run average is below the estimate (0.35x), comfortably inside the 2x go band.
The estimate covers the loop run only. The one-time build (bloat) call is a separate,
non-recurring cost that build_case.py does not meter; it does not enter the per-run
figure and is not part of the full-corpus run cost.

Extrapolation for the planned full run, at this measured per-run average and the
methodology target of 28 cases at 5 runs (140 runs): about $1.48, well under the
methodology's $4 to $5 envelope. This is an extrapolation, stated as such; the
authoritative full-corpus cost is the P9.4 run.

## 5. Three-point GO / NO-GO assessment

### A. COST HOLDS

Criterion: per-run average within 2x of $0.03 is GO; at or above 3x flags for scope
reconsideration.

Measured: per-run average $0.010570, which is 0.35x of $0.03.

Verdict: GO. The per-run cost is below the estimate, not merely within 2x.

### B. best_gen COHERENT

Criterion: across 5 runs per case, best_gen stable enough to report a finding. A
one-shot pattern is GO. Some cases being loop-load-bearing is also GO (that is a
finding). Incoherent wild variance making best_gen meaningless is NO-GO on methodology.

Measured: best_gen is 1 on all 15 runs, every case, zero run-to-run variance. The
pattern is one-shot across all three categories and all three difficulty levels.

Verdict: GO. best_gen is maximally coherent (a single value with no variance). The
finding it reports is the expected one-shot result, consistent with the existing
RESULTS.md.

### C. SUBSTANTIAL SPAN

Criterion: the bloat injected a real original-to-reference span on each case (room to
optimize) is GO. A case bloating to near-zero span is RESHAPE for that case (author a
richer reference before the full build).

Measured: cyclomatic deltas 23, 28, 23; logical_loc deltas 57, 64, 63. Every span is
substantial and inside the existing corpus range. No near-zero span.

Verdict: GO. The bloat tool injected a measurable, substantial span on every case at
construction. No case needs reshaping.

## 6. Scope of the finding (what the pilot does and does not establish)

What the pilot establishes:

- The build_case.py path runs end to end and produces standard-shape cases with
  substantial spans on the first attempt for all three categories sampled.
- The temporal-freeze discipline is executable and verifiable (commit before runs, with
  two independent orderings).
- The fixed-config run protocol is cheap (0.35x the estimate per run) and produces a
  coherent, zero-variance best_gen across 5 repeats per case.
- The cost extrapolation for the full run sits well inside the methodology envelope.

What the pilot does not establish, stated honestly:

- Because the three references are reused copies of existing corpus references (the P9.3
  reuse choice), the generation-count finding on these three is consistent with the
  existing 5-case RESULTS.md rather than independent new evidence. The roughly 17 new
  references the full build will author are new functions and could behave differently
  (a case could return baseline, or be loop-load-bearing); the methodology already
  commits to reporting the full distribution including any such case (Section 6 of the
  contract).
- build_case.py does not gate on span (methodology Section 3). The substantial spans here
  came from bloating already-rich references. For the full build, the substantial-span
  property depends on the author writing rich new references, which is the authoring
  discipline the contract assigns to the human, not a guarantee the tool provides.
- The multi-generation loop was not exercised (every case is one-shot to floor), so the
  pilot says nothing about loop behavior on a case that does not reach the floor in
  generation 1. That is an expected gap at single-function scope, not a defect.

---

## 7. Recommended verdict

GO on building the remaining references for the full corpus.

All three criteria are GO: cost holds at 0.35x the estimate, best_gen is coherent
(one-shot, zero variance across 15 runs), and every injected span is substantial. The
toolchain, the temporal-freeze discipline, and the fixed-config run-and-measure protocol
are validated end to end and are cheap enough that the full run is well inside budget.

The one carry-forward condition is not a blocker on the pilot but a discipline for the
full build: the roughly 17 new references must be authored to the reference rubric
(Section 4 of the contract), each a non-trivial representative of its category with a
substantial span, since build_case.py does not enforce span. The full distribution,
including any case where Darwin returns baseline or the loop is load-bearing, is reported
without exclusion per the contract. The authoritative results come from the P9.4
full-corpus run under one fixed config; the three pilot cases are real corpus cases and
remain, and their runs here are validation runs.
